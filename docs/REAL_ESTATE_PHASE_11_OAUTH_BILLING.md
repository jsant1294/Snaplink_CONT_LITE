# Phase 11 OAuth Completion, Marketplace Billing & Test Infrastructure

Phase 11 completes the OAuth foundation Phase 9 deliberately left partial, adds a marketplace billing model, and adds load/multi-office isolation test tooling. It does not touch contractor payment functionality, does not add any MLS/IDX vendor adapter, and does not begin Phase 12.

## OAuth completion

Phase 9 shipped authorization-code exchange only; consent, refresh, revocation, and connected-app administration were explicitly deferred. Phase 11 adds all of it to the existing `lib/real-estate/enterprise/oauth.ts` module — no OAuth table or function from Phase 9 was replaced, only extended, and the existing `authorization_code` grant path is unchanged.

- **Consent** (`real_estate_oauth_consents`, new): a membership's approved scopes per client, checked as a strict superset of any newly requested scopes (`hasValidConsent`). Approving a broader scope set later merges into the existing record rather than requiring re-approval of what was already granted.
- **Consent UI**: `/real-estate/oauth/authorize` renders the client name and requested scopes and posts an approve/deny decision to `/api/real-estate/oauth/authorize`, which redirects the browser back to the third party's `redirect_uri` with `code`/`state` (approve) or `error=access_denied`/`state` (deny) — the standard authorization-code redirect shape. Because this application has no end-user login session (PIN + membership headers only, see `lib/auth.ts`), the consent screen is reached from within an already-authenticated brokerage admin session, consistent with how every other Phase 9/10 admin surface is gated (`settings:manage`). A true third-party-initiated browser redirect into a logged-out session is out of scope until this app has real user authentication.
- **Refresh-token rotation**: `POST /api/v1/oauth/token` now accepts `grant_type=refresh_token`. Rotation is single-use: presenting an already-used or already-revoked refresh token is treated as theft/reuse and revokes every grant sharing that token's `familyId` (access and refresh, past and future), not just the one presented. This is exactly what the Phase 9 schema's `familyId` column was reserved for.
- **Revocation**: `POST /api/v1/oauth/revoke` (RFC 7009-shaped: `client_id`, `client_secret`, `token`) revokes a single token, or — if the token is a refresh token — its whole family. `revokeConsent` (used by connected-app admin) goes further: it revokes the consent record *and* every active grant for that client+membership in one call, so "revoke this app" actually removes access rather than just hiding it from a list.
- **Connected-app administration**: `GET/DELETE /api/real-estate/oauth/connected-apps` and the `/real-estate/settings/connected-apps` page list a tenant's approved apps (name, scopes, granted date) and let an admin revoke one.
- **Bearer authentication**: OAuth access tokens (`slk_oauth_...`) previously had no path to actually authenticate a request — `authenticateApi` only recognized API keys. `lib/real-estate/enterprise/security.ts` now branches on the token prefix: OAuth tokens are looked up in `real_estate_oauth_grants` (scope-checked, expiry-checked, revocation-checked) instead of `real_estate_api_keys`, with a conservative fixed per-minute rate limit (OAuth clients have no per-client `requestsPerMinute` column the way API keys do). `ApiPrincipal` gained optional `apiKeyId`/`oauthGrantId` fields (both were already only ever *set*, never read, elsewhere — this is a non-breaking widening).

## Marketplace billing model

`lib/real-estate/marketplace/billing.ts` adds plans, subscriptions, usage metering, and invoices — a billing *model*, not a payment integration. No price, currency default beyond ISO `usd`, MLS/CRM/e-signature vendor, or payment processor is hardcoded:

- `real_estate_billing_plans`: operator-entered `name`, `billingPeriod` (`monthly`/`annual`/`usage`), `amountCents` (validated as a non-negative integer supplied by the caller — never generated by this code), optional `meteredUnit` for usage plans, optional `providerKey` to tie a plan to a specific marketplace provider.
- `real_estate_billing_subscriptions`: tenant-scoped subscription to a plan, optionally tied to a specific marketplace installation.
- `real_estate_billing_usage_records`: append-only metered usage (`recordUsage`), summed per billing period when a usage-plan invoice is generated.
- `real_estate_billing_invoices`: generated via `generateInvoice`, which computes `amountDueCents` from the plan (flat) or from summed usage records × the plan's per-unit price (metered), then attempts to charge it.

**Payment-processor abstraction**: `PaymentProcessor` is a one-method interface (`charge`), following the exact pattern `ProductionEmailProvider`/`ProductionSmsProvider` already use in `lib/real-estate/integrations/providers.ts` — pluggable, with a safe `PreviewPaymentProcessor` fallback. Outside `NODE_ENV=production`, or when no processor has been registered via `registerPaymentProcessor`, every charge is handled by the preview processor (marks the invoice paid immediately, mirroring how preview-mode email/SMS "sends" immediately) so development and demos aren't blocked. **No real payment processor is wired in this phase** — per instructions, the SnapLink Contractor Stripe onboarding wizard belongs to a different application (SnapLink Core) and was not touched, referenced, or reimplemented here; a production integration plugs in later via `registerPaymentProcessor` without any schema or call-site change.

Routes: `GET/POST /api/real-estate/billing/plans`, `GET/POST /api/real-estate/billing/subscriptions`, `DELETE /api/real-estate/billing/subscriptions/{id}`, `GET/POST /api/real-estate/billing/invoices`. All require `settings:manage`.

## MLS/IDX adapter — intentionally not built this phase

Per explicit instruction, no MLS/IDX vendor adapter, credentials, pricing, attribution rule, or data-permission was invented. The Phase 10 provider-neutral foundation (`lib/real-estate/marketplace/mls.ts`: `MlsSyncAdapter` interface, cursors, entity mapping, conflict detection, `registerMlsAdapter`) is unchanged and ready to receive one. To unblock a concrete adapter in a future phase, the following must exist first and were not present in this repository or session:

1. A signed customer contract naming the specific MLS/IDX provider and the brokerage(s) it covers.
2. That provider's official API/feed documentation (auth method, endpoints, field dictionary, rate limits).
3. Real, provisioned credentials scoped to that contract (not shared/demo credentials).
4. The provider's data-license and display/attribution rules (MLS data is typically subject to strict compliance terms — e.g., listing attribution, agent display requirements, data-retention limits — that vary by MLS and must come from the provider/contract, not be assumed).

When those four exist, implementing the adapter is: write a class satisfying `MlsSyncAdapter.fetchChanges`, call `registerMlsAdapter(providerKey, adapter)` at process start, and add one `PROVIDER_CATALOG` entry in `lib/real-estate/marketplace/types.ts` with that provider's real capabilities and required scopes.

## Load and multi-office tenant-isolation testing

- **Automated (runs now)**: `tests/real-estate-db-integration.test.mjs` gained a Phase 11 test — gated on `REAL_ESTATE_TEST_DATABASE_URL` like every other DB-integration test in this suite — that inserts two offices under one tenant plus a third office under a different tenant, and proves: (a) office listings never cross tenants, (b) a property scoped to one office never resolves under a sibling office's scope (exercising the Phase 9 `real_estate_enterprise_resource_scopes` table), and (c) OAuth consents and billing subscriptions sharing the same client/plan stay strictly tenant-scoped.
- **Staging load test (requires an environment this session does not have)**: `scripts/real-estate-staging-load-test.mjs` runs a concurrent load test against a real `/api/v1` deployment (latency p50/p95/p99, success/rate-limit/error counts, throughput) and a black-box cross-tenant isolation check (lists every resource with two different tenants' API keys and asserts the returned external IDs never overlap). It requires `REAL_ESTATE_STAGING_BASE_URL`, `REAL_ESTATE_STAGING_API_KEY_A`, and (for the isolation check) `REAL_ESTATE_STAGING_API_KEY_B` belonging to a **different** tenant. None of these were available in this development sandbox, so **this script has not been executed against a live staging deployment** — it is ready for an operator to run once staging credentials exist. This mirrors the same limitation Phase 9's docs already flagged ("load-test execution against production are intentionally excluded").

## Migration and rollout

`drizzle/0010_phase11_oauth_billing.sql` is additive only (5 new tables, FKs/indexes scoped to those new tables) and must not be applied automatically. No backfill is required — existing OAuth clients/grants are unaffected, and billing has no rows until an operator creates a plan. Roll out the migration, then confirm `authenticateApi` still accepts existing API keys (unchanged code path) before enabling the OAuth consent UI for any real third-party integration partner.

## Known limits

No production payment processor, no MLS/IDX vendor adapter, and no staging load-test execution — all three require external inputs (a payment processor account, an MLS contract/credentials, and a staging deployment/credentials) that do not exist in this repository or session. Consent UI assumes an already-authenticated brokerage admin session rather than a standalone end-user login flow, matching this application's current PIN/membership auth model.
